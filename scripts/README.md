## Agent sign-in

Use the existing test-account password method in `scripts/lib/session.mjs`. It makes one password attempt for account 1 or 2. CAPTCHA and other failures stop visibly; there is no magic-link fallback, OTP route or admin client.

Configuration belongs in the ignored local env file: `APP_URL`, `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, and `TEST_USER_EMAIL` / `TEST_USER_PASSWORD` or `TEST_USER2_EMAIL` / `TEST_USER2_PASSWORD`. The local check uses account 2. Never print or commit a password, token, cookie header or cookie jar. No account creation, password change or meal write is part of a sign-in check.

- Without a browser, `signInTestClient(which)` returns `{client, user}`. When finished, use `await client.auth.signOut({scope: 'local'})`. The global scope would end other agents' sessions on that account.
- For a browser, `signInAsTestUser(which)` returns the cookie header generated by the installed SSR package, including chunking. Keep it in memory. Split each `name=value` pair at its first `=`, keep the pairs unchanged, and use `context.addCookies` with the local app URL. Do not put this header in logs or files. Rebuild an SSR client from that same in-memory jar for local-scope sign-out; do not sign in a second time just to obtain another client. Clear the browser context when finished.

With the disposable stack and its local app already running, the bounded check is:

```sh
MFA_TEST_DISPOSABLE=1 node --env-file=.env.test.local scripts/agent-sign-in-check.mjs
```

It validates **both** the app and Supabase URLs as loopback HTTP(S), without embedded credentials, before importing the Auth SDK/session helper or authenticating. It accepts no command-line options or production mode. All requests are restricted to those two origins and redirects are refused. It signs in once with `signInAsTestUser(2)`, rebuilds an SSR client from that in-memory jar, makes one authenticated `GET /api/today`, and signs out with local scope. Only the HTTP status and the first eight characters of the signed-in user's id are printed; the prefix is read locally from the fresh session. Any authentication, read or sign-out failure exits non-zero. Cookies are never printed or written to disk.

Production evidence is historical, not a command to run: the PM confirmed at 21:12Z on Nov 22 that GrokBot used judge 1 and judge 2 in emulated iPhone browsers to sign in and post without a human. The summary reports one browser-side call per sign-in, not a server-side request count or proof of this particular library path. The record is the PM's internal Nov 22 QA decision record; its raw QA report was not available to the PM. Playwright WebKit is not Safari, and real-device differences remain unproved. **Any future production action with a test account requires the owner's explicit yes.** Do not run or propose production verification by default. Provider rollout checks belong to their own approved work.
