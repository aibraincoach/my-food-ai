# Wall of Stupid

Tracks process failures so they don't repeat. One entry per incident. Newest first.

| Date | Who | What happened | Rule going forward |
|------|-----|---------------|--------------------|
| 2026-10-27 13:18 JST | PM, session 1 | Called a plan approved while listing edits it still needed. The owner asked whether the planner's corrected plan was ready. I answered that the plan was good, then listed three edits that still had to be made, then wrote a message to the planner that began "Approved with three edits". A plan that needs edits is not approved. The owner asked a yes/no question and the answer was no. Telling the planner "approved" while also asking for changes risked the planner copying the plan to the public repo unchanged, or not making the edits at all. | A review ends in one of two states. Approved means zero edits are needed, the plan is final, and the PM says so first. Not approved means the answer is no, the edits come first, and nothing is called approved until they are done and checked. The PM never says "approved with", "good, but" or "ready except". If a message contains a list of changes, the verdict is not approved. |
| 2026-10-27 10:35 JST | PM, session 2 | The PM wrote "BACKLOG.md sync" into the engineering backlog as an item, and the coder turned it into GitHub issue #27. Copying the backlog doc into the repo is PM housekeeping done on request. It is not engineering work, and no coder's pull request could close it. The owner had to point out that an engineering backlog is not the place for it. | Every backlog item is a problem an engineer solves in the codebase. Before adding an item, ask whether a pull request would close it. If not, it is not an item. Housekeeping, process, syncing documents, filming and anything the PM or the owner does stay out of the backlog. |
| 2026-10-27 10:20 JST | PM, session 2 | The coder reported that it had created GitHub issues #2 to #27 for the 26 backlog items and told the PM to put the numbers in the backlog doc. The PM replied "standing by" and did not edit the doc. The doc had no issue numbers until the owner asked why. The owner had already given the PM the information, and the backlog is the PM's one job. | When any report carries information that changes the backlog (issue numbers, a finished item, a new blocker, a changed decision), update the backlog doc in the same turn, before replying, and rewrite the Last edited line. Standing by or collecting context never replaces updating the backlog. After every report, check it against the doc before saying anything else. |
