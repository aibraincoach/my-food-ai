# Owner phone checks

These five acceptance conditions remain unproven on physical phones. Browser emulation, API success and the recorded desktop-browser rehearsal do not close them. Use the installed Home Screen app and the same existing account; do not clear browser storage, reinstall or sign out between persistence checks.

## Fast sequence

1. **Phone A: one launch checks three things.** Turn Wi-Fi off, start a screen recording, and open the installed app on mobile data. For #221, an account previously signed in on this phone should open the feed without signing in again. For #222, measure icon tap to the first real meal photograph, decoded and visible, rather than a grey box or generated nutrition card; the issue requires two seconds. Record the network type and whether this was a cold or warm visit. For #108, check the top title below the clock/notch and the whole bottom bar above the home indicator. Record phone model, OS and screen size. A second phone that never signed in is expected to sign in once.
2. **Use the actual camera on A.** Open + → Camera, permit the camera if requested, check a live view, flip cameras and return to the rear camera, then photograph a simple meal. Type a caption and ensure Post remains reachable with the keyboard open. Post it. The feed must show that exact photo; detail must retain it and the analysis must settle. Check the capture sheet and a detail edit sheet against the clock and home indicator as well. Gallery upload on a desktop does not prove this camera path. On an iPhone, also open the drink sheet and Days story to check their safe areas. Fit at both 390×844 and 430×932 needs those actual sizes; one phone cannot prove both.
3. **Enable notifications, then make a second post.** If permission was requested after the first post, finish granting it before this second post. That avoids a meal finishing before a subscription exists. Post a small meal, immediately send the installed app to the background or lock the phone while analysis runs, and leave it there. Do not force-quit during this push check. The expected notification is the generic “Your meal is ready” (or “Your meal needs a reply” for a question), not a thumbnail or meal text. Tap it and verify that it opens this second post. This proves #22 only when the notification arrived while the app was in the background. Note the posting and notification times. If it does not arrive, record notification permission, Focus state and whether the post reached ready before diagnosing the delivery path.
4. **While that analysis runs, use phone B.** Install/open the Home Screen app, sign in once if needed, close it and reopen it. It must retain the session, and A must still be signed in. If B is an iPhone of the other required size, repeat the top/bottom fit check. This covers the second-device portion of #221 without waiting idle for push.
5. **Finish with reopen and refresh checks on A.** After checking the notification, force-close and reopen A once; it must still be signed in. Repeat the mobile-data image timing for the warm visit. Later, reopen after the access token has expired to test renewal, without signing out or clearing storage; record the interval. The project helper's freshly issued token expires in one hour under the current default, but the device's actual renewal behavior remains the evidence.

6. **Scan a real pack (#212).** In the capture sheet, scan the pack in Barcode mode, then photograph the same barcode in Photo mode. Record the digits, product name, portion and nutrition shown in each case. For a code with no database product, choose “Photograph the nutrition label”, capture its panel, name it and post two servings. Record the label reading and the posted nutrition; the original pack/label photo must appear. This requires the real phone camera; the coder’s UPC-A and FDA fixtures in emulation do not prove it.

7. **Use a real half-eaten plate.** Photograph the meal before and after eating and verify the consumed estimate. The previous same-image-twice fixture proves mechanics, not real remainder accuracy. If the result is wrong, exclude this flow from the demo script. The latest owner also requests multiple after-meal photos and the wording “leftovers (not eaten)”; those are pending backlog changes, not already shipped behavior.

Report observed behavior and timestamps for every failure. A screen recording lets launch timing, safe areas and the real camera be checked without repeating the whole sequence. Do not include account identifiers in shared evidence.

## Preflight and platform limits

A read-only production preflight found all three variable names the push code actually uses: `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT`. No values were copied. This configuration check is not delivery evidence. The wake remained enabled after the production analysis tests.

Apple supports standards-based Web Push for Home Screen web apps on iOS/iPadOS 16.4 or later, with permission requested from a direct user interaction. An ordinary Safari tab is not an equivalent background-push test. [WebKit platform announcement](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)
