The PR reorders and refines optimistic bookmark handling in PostActions.tsx:

Handling un-saving immediately when the post is visibly saved.

Fast-failing bookmark clicks when a post is already in a failed status.

Adding a 120-second timeout to revert optimistic state if an unready post never settles.

Cleaning up listeners when an unready post resolves or fails.

Potential Issues
Memory leak on component unmount

When an unready post's save action is clicked, event listeners (post-settled, post-ready) and a 120-second timer (setTimeout) are registered on window. If the user navigates away or the feed unmounts before 120 seconds or before the post settles:

The listeners remain active on window.

When triggered, they will attempt state updates (setBookmark) on an unmounted component.

The cleanup function should be stored in a ref so the main useEffect cleanup hook can call it on unmount.

Optimistic state toggle in beginBookmark

In beginBookmark:

ts
export function beginBookmark(state: BookmarkState): BookmarkState {
  return state.pending ? state : {id: state.id ? null : 'pending', pending: true};
}

When visibleSaved is true:

ts
if(visibleSaved){
  const next=beginBookmark({...previous,id:previous.id});
  ...

If previous.id was truthy (e.g., 'meal_123' or 'unknown'), beginBookmark sets next.id to null.

If bookmark.id === 'unknown' but saved === true, previous.id is 'unknown' (truthy), flipping next.id to null.

However, if bookmark.id is null but visibleSaved is true because of initial state edge cases, passing {...previous, id: null} into beginBookmark would cause beginBookmark to treat it as an addition (id: 'pending'). Explicitly ensuring previous.id is truthy before passing it, or passing an explicit intent (action: 'save' | 'unsave'), would avoid relying on the truthiness toggle of id.

Duplicate listener execution

In onSettled:

ts
if(settled?.status==='ready'){
  window.dispatchEvent(new CustomEvent('save-meal',{detail}));
  return;
}

Because both post-ready and post-settled are registered, if an external producer emits both post-ready and post-settled in sequence (or vice-versa), cleanup() prevents duplicate calls only if the first event cleans up before the second fires. The code currently does cleanup() before dispatching in both callbacks, which avoids duplicate dispatches.
