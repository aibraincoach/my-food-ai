This pull request addresses issue #189 by improving USDA FoodData Central (FDC) candidate food selection and tightening LLM vision portion estimations for breakfast items. Overall, the implementation cleanly threads query strings through the persistence and background worker pipelines while directly solving the misclassification issues.

Core Architecture and Pipeline Flow

Pipeline Propagation:

persist.ts, jobs/correct.ts, and jobs/recompute.ts now pass item.name into chooseBestMatch(foods, item.name).

When query is omitted or whitespace-only, chooseBestMatch maintains deterministic backwards compatibility by evaluating USDA DATA_TYPE_RANK directly.

Scoring Logic (scoreFoodMatch):

Computes baseline relevance via word token overlap using a tokenized Set of description words.

Evaluates targeted heuristics:

Salads: Down-weights dressings (-8) and sandwich spreads (-6); penalizes compound salads (tuna, ham, potato, egg) unless present in the user query (-4); boosts lettuce and side salads (+3).

Coffee: Heavily penalizes milk/silk/soymilk (-8) and pepper spices/sodas (-8) when the query denotes plain coffee; boosts black coffee (+4) and low-calorie beverages (+3).

Eggs: Penalizes condiment ketchup (-10) unless the query specifically requested it without egg context; boosts scrambled preparations (+4).

Incorporates rankOf(food.dataType) * 0.01 as a fractional tie-breaker.

Prompt Anchoring (identify.ts & correct.ts):

Adds concrete portion boundaries to guard against multi-serving overestimation: 5–15 g for thin ham slices, 40–70 g for single Japanese toast slices, ~50 g per scrambled egg, and ~240 g per cup of coffee/tea.
