Overview of PR #299

PR #299 introduces durable background photo uploads . Selected photos are staged immediately upon selection, persisted along with upload checkpoints in IndexedDB, and tracked via byte-level progress . The user can close the composer while uploads continue in the background, drafts survive page reloads/disconnects, and optimistic feed cards stay hydrated through server confirmation .

The PR is architecturally well-designed and directly addresses resilient offline-first upload UX. However, several critical race conditions, resource leaks, and edge-case bugs should be addressed before merging .

Critical Issues & Correctness Bugs
1. Stale File Array Mapping When Storing in IndexedDB

In src/lib/posts/upload-manager.ts inside initialize:

typescript
data.files = data.files.map((file, index) => new File([file], file.name ?? `meal-${index}.jpg`, { type: file.type }));

In IndexedDB (uploadStore), data.files contains File / Blob instances.

When data.files[0] has no custom name, accessing file.name is fine, but in some browser engines (such as WebKit / Safari), deserialized IDB Blobs/Files may lose their prototype or property descriptors if stored as plain Blobs.

More importantly, in stage():

typescript
else if (files.length !== entry.data.files.length || files.some((file, i) => file !== entry!.data.files[i]))

When an entry is reloaded from IndexedDB, File identity checks (file !== entry.data.files[i]) will evaluate to true when compared against newly supplied File objects from file pickers, triggering recreation of drafts and revoking preview URLs unnecessarily .

2. Re-entrancy and Unhandled Race in UploadManager.run() / process()

In src/lib/posts/upload-manager.ts:

typescript
private run(entry: Entry): Promise<void> {
  if (entry.active) return entry.active;
  const task = this.process(entry);
  entry.active = task;
  void task.finally(() => {
    entry.active = null;
    if (!entry.deleted && !entry.finished && entry.data.posted && entry.data.state === 'uploaded') void this.run(entry);
  });
  return task;
}

If process() fails or encounters an unhandled exception, task.finally is executed. But notice: run() does not catch rejected promises returned by task inside .finally() or at the call site.

In process():

typescript
if (version !== entry.version) {
  attempt = -1;
  continue;
}

If a user edits the caption rapidly, entry.version increments repeatedly. Setting attempt = -1 triggers an infinite loop inside the 3-attempt for loop if entry.version continually updates faster than network responses .

3. Memory Leak: Blob URL Revocation in LightComposer.tsx and UploadChip.tsx

In LightComposer.tsx:

typescript
const [initialShots] = useState<Shot[]>(() => resumed.current?.files.map(file => ({ file, previewUrl: URL.createObjectURL(file) })) ?? []);

Creating object URLs inside initializers or components without revoking them on unmount (useEffect(() => () => URL.revokeObjectURL(url), [])) leaks memory in Single Page Application navigation .

In UploadChip.tsx:

typescript
const observer = new MutationObserver(update);
observer.observe(document.body, { childList: true, subtree: true });

Observing the entire document.body for childList and subtree on every DOM mutation is an expensive operation on mobile browsers . This observer fires continuously during animations, hydration, and user typing .

Concurrency & Data Flow Risks
4. Subscriptions & Event Listeners Cleanups in UploadChip.tsx

In src/components/UploadChip.tsx:

typescript
useEffect(() => {
  const db = createClient();
  void db.auth.getUser().then(({ data }) => {
    if (data.user) void uploadManager.initialize(data.user.id);
  });
  const { data: { subscription } } = db.auth.onAuthStateChange(event => {
    if (event === 'SIGNED_OUT') void uploadManager.clear();
  });
  ...
}, []);

UploadChip is rendered inside NavigationControls, which is mounted globally . However, if NavigationControls remounts or is placed in multiple layouts, uploadManager.initialize will be invoked concurrently with different lifecycle triggers .

Consider moving auth initialization of uploadManager to a top-level provider or dedicated Auth listener service rather than inside a UI chip component .

5. Optimistic Card Polling Timeout in UploadHydratedCard

In src/components/Feed.tsx:

typescript
function UploadHydratedCard(...) {
  ...
  useEffect(() => {
    ...
    if (live && Date.now() - started < 120000)
      timer = setTimeout(() => { void read(); }, 2000);
  }, [post, upload.postId]);
}

Polling getPostCard(db, upload.postId!) every 2 seconds for up to 2 minutes generates up to 60 Supabase DB queries per active upload .

If multiple posts are queued/uploaded or network latency is high, these interval timers can cascade . Use Supabase realtime channel updates for status changes (post.status === 'ready') and fall back to exponential backoff polling (e.g., 2s, 5s, 10s, 30s) instead of fixed 2s loops .

Security, Storage & Protocol
6. Upsert Capability on Storage Uploads

In src/lib/media/storage.ts:

typescript
supabase.storage.from(BUCKET).createSignedUploadUrl(originalPath, { upsert: true })

Enabling upsert: true on signed upload URLs solves the 503 retry issue when a reservation is re-used .

Security Check: Ensure Supabase RLS Storage policies strictly restrict write access to the specific authenticated userId matching userId/postId/position.jpg to prevent malicious overwrites of another user’s objects .
