## 0. Run rules

- **One run, zero stops.** One prompt, to the end. The coder's final report lists every item number 0 to 10 as done or not done with PR number and head SHA, the reviewer and verdict per PR, the production checks of items 6 to 10 with their evidence lines, and the list of PRs awaiting merge orders in ascending PR number. No interim gate exists; the coder sends a progress note when it likes and never waits for a reply.
- **One shared file, and how its PRs merge.** Items 1, 2, 3, 4 and 5 all add tokens to `src/lib/theme/tokens.ts` (and its generated `tokens.css`); apart from that file their "Touches" lists are disjoint. So the tokens are not added five times: item 0 is a tokens-only PR, cut from `main` first, carrying every token of section 2.0 and the regenerated `tokens.css` and nothing else. Items 1 to 5 are cut from item 0's head in fresh worktrees under `../my-food-ai-wt/<item>`, open their PRs against item 0's branch, and say "stacked on #<item 0's PR> at <head SHA>" in the PR text and the report; they add no token themselves. Item 0 merges first (section 6); GitHub then retargets items 1 to 5 to `main` with their heads unchanged, and none of them conflicts with another, because the only file they shared is already on `main` through item 0. Items 2, 3 and 4 share one contract instead of code: the `open-entry` window event defined in item 2, so each lands alone and the whole works once all three are on `main`. Items 6 and 7 are cut from `main` (item 7 continues PR #197 on its existing branch). Items 8 to 10 are production checks that produce a PR only if they find a defect.
- **Heads stay valid, and a head updated from main gets its own receipt.** A PR is never rebased, amended or force-pushed after its review starts. A fix after review goes on as a new commit and is reviewed again on its new head. A branch is brought up to date from `main` only when GitHub reports it not mergeable; then the coder merges `main` in with a merge commit, which is a new head. Because the merge guard needs a receipt on the exact head, that new head is not exempt: the coder posts the merge commit and its SHA, the same reviewer runs a confirmation pass on that head scoped to the merge commit's diff against its first parent (the conflict resolution and nothing else) and posts the receipt "BLOCKERS: NONE" on that SHA, Vercel builds it on its own, and the coder reports the new head with the receipt and the check status. The PM's order then names that head. No head is merged on an older head's receipt.
- **The merge guard, for every PR including #197.** The coder merges nothing without an order. When all code is written, reviewed and tested, the coder reports; the planner evaluates the report against this plan; the PM issues one order per PR naming one PR and one head SHA, in ascending PR number. An order is executable only when all three hold on that exact head: the reviewer's receipt reading "BLOCKERS: NONE" on that head, a clean mergeable state, and green checks (Vercel included). The coder executes an order only after reading the PR's head from GitHub and finding the same SHA and those three; merge commits only. PR #197 has none of the three on `347c104` today (its receipt is on `7e9231e`); item 7 produces them on its final head.
- **Reviews.** Run in a sub-agent beside the build, never blocking it. One external reviewer per PR, one pass per head, to zero blockers; the same reviewer confirms fixes. Routing: PPLX (`skills/pplx-review`) first; if it cannot run, AGY (`skills/agy-review`); if that cannot run, Codex (`skills/codex-review`); all from `main`. Defects are fixed inside the review loop.
- **Tests and page looks after all code is written.** The coder may run tests for itself at any time; the test pass the report cites, and every page look, come after the last item's code is written. A page look is one comparison of the built page against the designer's frame at 390 px wide in Chrome device emulation, signed in as the test account, reported as a list of differences on the PR; no image stored; Playwright never. Until item 6 is done, the page looks use the app served locally (`next build && next start` against the real project) with the session cookie from `scripts/lib/session.mjs` set in the emulated browser; once item 6 is done they may use production after the merge phase. Items 1 to 5 each get a page look against their frames (2a and 2b; 2c and 2d; 2h; 2i; 2e, 2f and 2g). Items 6 to 10 run their production checks after the merge phase, item 6 first.
- **Tests.** New tests only for data rules and access: item 3 (migration 0019 and the drink post), item 4 (the scanned post and migration 0020). Item 7 keeps `tests/fdc-match.test.mjs` from PR #197. None for layout, CSS, motion or wording. - **Halts.** Only the three legal halts: a review tool unavailable (route to the next, never wait); a stated fact or premise false (the report says which); an operation that would contact a customer or breach a prohibition. A halt stops only its item; every independent item continues.
- **Customer contact.** None. Production checks use the test accounts only. Item 6's sign-in link, if used, is generated and opened by the coder, never mailed. The owner's own post in #189 is read, never changed, and nothing is sent to anyone.

## 5. Risks

3. **Two writes without one transaction** (item 3): a drink post without its intake row. Early test: the drink-post test. Fallback: the compensating delete in the route; a leftover row with no post is harmless and is reported.

Early test: the first scan in emulation with the UPC-A image from PR #165's test shown to the camera, and one shot of it in Photo mode; the sheet must stay responsive and a shot with no code must not wait more than one second for the decode. 8. **A production check fails for a reason outside its item** (items 8 to 10), for example the queue is idle because no tick ran. The check is repeated once after a tick through `/api/jobs/tick`; a second failure is a defect and gets its PR.
