## 0. Run rules

- **One run, zero stops.** One prompt, to the end. The coder's final report lists every item number as done or not done with PR number and head SHA, the reviewer and verdict per PR, the `/api/health` result, and the list of PRs awaiting merge orders in dependency order. No interim gate exists; the coder sends a progress note when it likes and never waits for a reply.
- **Sequencing and stacking.** Each item names its dependencies. The coder starts every item now. An item with no unmet dependency is cut from `main`. An item whose dependency is not yet on `main` is cut from that dependency's open PR head, its PR is opened against the parent's branch, and its PR text and the report say "stacked on #N at <parent head SHA>". The waves in section 1 are a picture of the dependency order only; nothing waits for a wave. Items that run in parallel touch disjoint files (listed per item under "Touches").
- **Heads stay valid.** A parent is never rebased, amended or force-pushed after a child is cut. A fix after review goes on the parent as a new commit. Each child then merges the parent's new head in with a merge commit, never a rebase, and is reviewed again on its new head. Bringing `main` into a branch earns no new review.
- **Merge phase, at the end.** The coder merges nothing without an order. When all code is written, reviewed and tested, the coder reports; the planner evaluates the report against this plan; the PM issues one order per PR, naming one PR and one head SHA, in dependency order. When a parent merges with a merge commit, GitHub retargets its children to `main` with their heads unchanged, so each receipt still names the head being merged. The coder executes an order only after reading the PR's head from GitHub and finding the same SHA, the receipt on that head, a clean mergeable state and green checks; it merges with merge commits only and never rebases to retarget. The owner relays prompts and issues no merge order. The intended order is in section 6.
- **Worktrees.** Every PR is built in a fresh worktree under `../my-food-ai-wt/<item>`, cut from `main` or from the parent's head as above. Leftover worktrees are removed before the first PR.
- **Reviews.** Run in a sub-agent beside the build, never blocking it. One external reviewer per PR, one pass per head, to zero blockers; the same reviewer confirms fixes. Routing: PPLX (`skills/pplx-review`) first; if it cannot run, AGY (`skills/agy-review`); if that cannot run, Codex (`skills/codex-review`); all from `main`. Defects are fixed inside the review loop.
- **Tests and page looks after all code is written.** The coder may run tests for itself at any time; the test pass that the report cites, and every page look, come after the last item's code is written. A page look is one comparison of the built page (the app served locally with `next build && next start` against the real project, or production once merged) against the designer's frame at 390 px wide in Chrome device emulation, signed in as the test account, reported as a list of differences on the PR; no image stored; Playwright never. Production-only checks (item 2's browser check, item 14's after() test, items 15 and 29's scripts, item 35's demo runs) run after the merge phase.
- **Tests.** New tests only for sign-in and access, migrations and data rules: items 3, 4, 10, 12, 14, 16, 22, 28, 31, 32. None for layout, CSS or wording. Database tests run SQL through `psql` against `SUPABASE_DB_URL` inside one transaction ending in `rollback`, impersonating a user with `set local role authenticated; select set_config('request.jwt.claims', '{"sub":"<uuid>","role":"authenticated"}', true);`; each is a `.mjs` under `tests/` that spawns `psql` and asserts on its output. Items 14 and 31 add the end-to-end tests that use the real project with the test accounts.
- **Halts.** Only the three legal halts: a review tool unavailable (route to the next, never wait); a stated fact or premise false; an operation that would contact a customer or breach a prohibition. A halt stops only its item; every independent item continues.
- **Customer contact.** None. Auth confirmation mail stays off. Web Push (item 24) goes only to subscriptions the user created on their own device.
- **Cleanup.** Each worktree and local branch removed once its PR is pushed; each remote branch deleted after its merge; `scripts/cleanup.sh` is the last command of the run.
- **Variables.** The owner supplies keys only, in `.env.local`. The coder verifies production variables through `/api/health` and creates or updates only what is missing through the Vercel REST API project environment-variables endpoints with the project-scoped `VERCEL_TOKEN`; the Vercel CLI is never used. Migrations are applied with `psql` against `SUPABASE_DB_URL` in numeric order, each when the merge order for its PR arrives and before that merge, and the coder's reply to the order says it was applied. `.env.example` gains every new name; nothing is committed with a value. New names: `APP_URL` (item 2, if not already added), `ADMIN_EMAIL` (item 9), `WORKER_CONCURRENCY` (item 15), `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` (item 24), `MODEL_API_BASE_URL` (item 31).
- **Public docs.** No host names, account or billing detail, personal names or personal data under `docs/` or in the README. Item 34 extends this to every file on `main`.

## 5. Risks

1. **A screen PR breaks a Run 1 flow** (sign-in, posting, the realtime refresh). Early test: the page looks post a meal as the test account against the real project. Fallback: fixed on that PR's branch inside the review loop.
2. **A stacked chain grows long** (detail → thread → thumbs → strip → push) and a fix on the parent forces a merge-and-re-review down the chain. Early test: none; it is the cost of no stops. Fallback: each child merges the parent's new head once, at the end, before its review on the final head.
3. **`ImageResponse` does not render Manrope or the layout** (P4). Early test: item 17 renders one card locally before wiring `markReady`. Fallback: `@resvg/resvg-js`; the live `ResultsCard` stays as the caption-only image if both fail.
4. **The worker's time budget** under twenty posts (item 15). Early test: the load test. Fallback: `WORKER_CONCURRENCY` stays 1 and the traffic line covers the wait.
5. **The after() test cannot build the server cookie** (item 14). Early test: the first run of `after.test.mjs`. Fallback: the test signs in through the real sign-in page with a headless fetch of the form action and reuses the `Set-Cookie` it returns; if that also fails the test is reported not done and P2 rests on the Wave 0 evidence.
6. **Spark drifts between repeats** (item 20). Early test: two posts of `eval/photos/01.jpg`. Fallback: the ≥ 0.85 copy path bypasses re-estimation; if the similarity never reaches it, the threshold constant is lowered to the measured score and recorded in the code comment.
7. **iOS push and the live viewfinder** (items 24, 30) cannot be proven in emulation. Early test: the owner's phone. Fallback: push is below the cut; the viewfinder falls back to the picker by design.
8. **Outline PNGs from Run 1 do not align** with the box scaling (item 12). Early test: the first detail page look. Fallback: a rounded rectangle in the outline colour where the mask layer is missing or mis-sized.
9. **Recorded fixtures drift from the live API** (item 31). Early test: `scripts/record-fixtures.mjs` is re-run once in item 35. Fallback: the tests assert shape, not exact numbers.
