## 0. Run rules

- **One run, zero stops.** One prompt, to the end. The coder's final report lists every item 0 to 7 as done or not done with PR number and head SHA, the reviewer and verdict per PR, the production checks of item 7 with their evidence lines, which premises were false, and the PRs awaiting merge orders in ascending PR number. Progress notes are welcome and never wait for a reply.
- **Branches and the shared files.** Item 0 is a tokens-only PR cut from `main`. Items 1, 2 and 3 are cut from item 0's head and touch disjoint files apart from `tokens.ts`, which they do not edit. Items 4 and 5 both change files item 1 rewrites (`PostMenu.tsx`, `Carousel.tsx`, the feed row, `CaptureSheet.tsx`), so they are cut from item 1's head; item 6 changes item 5's carousel and sheet, so it is cut from item 5's head. **Every PR targets `main`** (no PR targets another branch; the retarget trap of Run 3 is not repeated). A child PR's diff shows its parent's commits until the parent merges; the PR text says "contains #<parent> at <parent head SHA>; merge after it" and the reviewer is told to review the child's own commits only (the receipt names the child's head). PRs are opened in item order, so ascending PR number is the merge order (section 6). Worktrees under `../my-food-ai-wt/<item>`.
- **Cross-item contracts instead of shared edits.** Item 1 renders from fields that other items supply: `kind` (P4) and `foodWaterMl`, `dayHydration` (item 2), `saved_meal_id` (item 4), `count_text` and `not_eaten` on media (item 5). A field that is absent renders nothing; nothing breaks when a child is not merged yet. The window events `save-meal`, `log-again` and `open-saved` (item 1 dispatches; item 4 listens) follow the `open-entry` pattern. The results card takes a data object with an optional `footer` (item 2 defines; item 5 fills).
- **Heads stay valid; an updated head gets its own receipt.** As Run 3: no rebase, amend or force-push after review starts; a fix is a new commit reviewed on its new head; a branch is brought up from `main` only when GitHub reports it not mergeable, by a merge commit, and that head gets a confirmation receipt scoped to the merge commit's diff against its first parent. A parent's fix after a child is cut: the child merges the parent's new head in with a merge commit and is reviewed on its new head.
- **The merge guard.** The coder merges nothing without an order. After the report and the planner's evaluation, the PM issues one order per PR naming one PR and one head SHA, in ascending PR number; executable only with the reviewer's receipt "BLOCKERS: NONE" on that exact head, a clean mergeable state and green checks (Vercel included); merge commits only.
- **Reviews.** In a sub-agent beside the build, never blocking it. One external reviewer per PR, one pass per head, to zero blockers; the same reviewer confirms fixes. Routing: PPLX (`skills/pplx-review`) first; if it cannot run, AGY (`skills/agy-review`); if that cannot run, Codex (`skills/codex-review`), which is eligible only when the coder is not an OpenAI model (the contract's rule). Nobody waits for a tool to recover: when no eligible tool can run at the moment a review is reached, that is the first legal halt for that PR's review only; the coder records it, keeps building every other item, retries the route once more when the next PR's review is reached, and the report names every PR left without a receipt. Defects are fixed inside the review loop.
- **Tests and page looks after all code is written.** As Run 3: the cited test pass and every page look come after the last item's code; a page look is one comparison of the built page against the frame at 390 px in Chrome device emulation, signed in as the test account through `scripts/browser-session.mjs` (PR #203), reported as a list of differences on the PR; no image stored; Playwright never. None for layout, motion or wording. Database tests follow the Run 2 pattern (`.mjs` under `tests/`, `psql` in one transaction ending in `rollback`, impersonation through `set local role authenticated` and `request.jwt.claims`).

## 4. Model API usage

Two new Spark calls, both `.ts` modules with strict schemas beside them, explicit low reasoning, through `spark.ts` and `recordCall`; the fake answers them by name (P12).

**`label`** (item 3). Instruction: read only what the printed nutrition facts panel states; never estimate; null where unreadable. Output `{ is_label: boolean, serving: { amount: number, unit: 'g' | 'ml' } | null, per_serving: { kcal: number | null, protein_g: number | null, carbs_g: number | null, fat_g: number | null, fibre_g: number | null, sugar_g: number | null, sodium_mg: number | null } | null, product_name: string | null, box: { x: number, y: number, w: number, h: number } | null }` (box in fractions of the image, for the accent frame).

**`remainder`** (item 5). Input: the not-eaten photo and the item list as "index · name · grams". Instruction: for each listed item, estimate what remains in this photo in grams relative to the grams given (0 when nothing remains; never more than given); when the item is countable (slices, pieces, eggs, rolls), give the count seen in the meal photo as `total_count` and the count remaining as `remaining_count` with the unit word; no advice, no other text. Output `{ items: [{ index: integer, remaining_grams: number, total_count: integer | null, remaining_count: integer | null, unit: string | null }] }`.

The identify schema gains `nutrition_label: boolean` (item 3) and its fixture is updated; the correct prompt gains one sentence for an added photo (item 6); the same-meal and search-query prompts are unchanged. Every one of these passes the real-model gate of section 0 before its PR's receipt.
