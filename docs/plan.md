## 0. Run rules

- **One run.** One prompt, to the end. The coder's final report lists every item number as done or not done with PR number and head SHA, the reviewer and verdict per PR, the `/api/health` result, and the list of PRs awaiting merge orders. Interim reports are sent at the end of each wave (section 1) with the same content for that wave's PRs.
- **Sequencing.** Each item names its dependencies. An item starts when all of them are on `main`; items with no unmet dependency run in parallel. Section 1 groups items into waves only to show the resulting picture; the rule is the dependency list, not the wave. Items that can run in parallel touch disjoint files (listed per item under "Touches"). Nothing is ever stacked: an item whose dependency is not on `main` waits for the merge, and the coder builds other items meanwhile.
- **Merges.** The coder merges nothing without a merge order. For each PR the coder reports PR number and head SHA with the reviewer's zero-blocker receipt on that exact head; the planner evaluates the report against this plan; the PM issues each merge order, naming one PR and one head SHA, from that evaluation and that receipt. The coder executes an order only after reading the PR's head from GitHub and finding the same SHA, the receipt on that head, a clean mergeable state and green checks. The owner relays prompts and issues no merge order. Docs PR #1 is first in the sequence: the coder brings `main` into `docs/fleet-initial` if it conflicts (no new review for that) and reports its head. After #1 merges, the review skills and `scripts/cleanup.sh` are read from `main`; until then from the branch in a side worktree. The intended sequence is in section 6.
- **Worktrees.** Every PR branches from `main` in a fresh worktree under `../my-food-ai-wt/<item>`. Leftover worktrees are removed before the first PR.
- **Reviews.** Run in a sub-agent beside the build, never blocking it. One external reviewer per PR, one pass per head, to zero blockers; the same reviewer confirms fixes. Routing: PPLX (`skills/pplx-review`) first; if it cannot run, AGY (`skills/agy-review`); if that cannot run, Codex (`skills/codex-review`). Defects are fixed inside the review loop.
- **Build first, then test and look.** Within a wave, every PR is built before that wave's tests and page looks run; tests, page looks and the wave report come at the end of the wave, because a PR that changes a page gets its one look before its merge order. A page look is one comparison of the built page against the designer's frame at 390 px wide in Chrome device emulation, signed in as the test account (item 2), reported as a list of differences on the PR; no image stored; Playwright never.
- **Tests.** New tests only for sign-in and access, migrations and data rules: items 3, 4, 10, 12, 14, 16, 22. None for layout, CSS or wording. Database tests run SQL through `psql` against `SUPABASE_DB_URL` inside one transaction ending in `rollback`, impersonating a user with `set local role authenticated; select set_config('request.jwt.claims', '{"sub":"<uuid>","role":"authenticated"}', true);` so row-level security is exercised; each is a `.mjs` under `tests/` that spawns `psql` and asserts on its output. Item 14 adds the end-to-end tests that use the real project with the test accounts.
- **Halts.** Only the three legal halts: a review tool unavailable (route to the next, never wait); a stated fact or premise false; an operation that would contact a customer or breach a prohibition. A halt stops only its item; every independent item continues.
- **Customer contact.** None. Auth confirmation mail stays off. Web Push (item 24) goes only to subscriptions the user created on their own device.
- **Cleanup.** Each worktree and local branch removed once its PR is pushed; each remote branch deleted after its merge; `scripts/cleanup.sh` is the last command of the run.
- **Variables.** The owner supplies keys only, in `.env.local`. The coder verifies production variables through `/api/health` and creates or updates only what is missing through the Vercel REST API project environment-variables endpoints with the project-scoped `VERCEL_TOKEN`; the Vercel CLI is never used. Migrations are applied with `psql` against `SUPABASE_DB_URL` in numeric order, each when the merge order for its PR arrives and before the merge is executed, and the coder's reply to the order says it was applied. `.env.example` gains every new name; nothing is committed with a value. New names: `TEST_USER_EMAIL`, `TEST_USER_PASSWORD`, `TEST_USER2_EMAIL`, `TEST_USER2_PASSWORD`, `APP_URL` (item 2), `ADMIN_EMAIL` (item 9), `WORKER_CONCURRENCY` (item 15), `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` (item 24).
- **Public docs.** No host names, account or billing detail, personal names or personal data under `docs/` or in the README.

## 5. Risks

1. **A screen PR breaks a Run 1 flow** (sign-in, posting, the realtime refresh). Early test: the Wave 1 page looks post a meal as the test account on production. Fallback: fixed on that PR's branch inside the review loop.
2. **`ImageResponse` does not render Manrope or the layout** (P4). Early test: item 17 renders one card locally before wiring `markReady`. Fallback: `@resvg/resvg-js`; the live `ResultsCard` stays as the caption-only image if both fail.
3. **The worker's time budget** under twenty posts (item 15). Early test: the load test. Fallback: `WORKER_CONCURRENCY` stays 1 and the traffic line covers the wait; nothing runs outside Vercel and Supabase.
4. **The after() test cannot build the server cookie** (item 14). Early test: the first run of `after.test.mjs`. Fallback: the test signs in through the real sign-in page with a headless fetch of the form action and reuses the `Set-Cookie` it returns; if that also fails the test is reported not done and P2 stays a premise.
5. **Spark drifts between repeats** (item 20). Early test: two posts of the same fixture plate. Fallback: the ≥ 0.85 copy path bypasses re-estimation; if the similarity never reaches it, the threshold constant is lowered to the measured score of the fixture pair and recorded in the code comment.
6. **iOS push** (item 24). Early test: none possible in emulation; the owner's phone. Fallback: below the cut; the demo shows the analysis landing by returning to the app.
7. **Outline PNGs from Run 1 do not align** with the box scaling (item 12). Early test: the first detail page look. Fallback: a rounded rectangle in the outline colour where the mask layer is missing or mis-sized; the chip and tap-to-edit still work.
